# Languages: Exhibit in English and Spanish

The full design (a project). The owner's decisions are marked **(owner)**. Everything else is the
designer's call and can be corrected.

## 1. Intent

Exhibit speaks the owner's language. Every word the window shows is available in US English and in
Spanish. **(owner)** The information TMDB provides follows the same choice: titles, overviews,
genres, episode names and posters. **(owner)** The language is a setting the owner sets once, or
rarely, in Settings. **(owner)**

Spanish comes in two regional choices, Spain and Latin America, because they really differ:
TMDB calls Fight Club "El Club de la Lucha" for `es-ES` and "El club de la pelea" for `es-MX`, and
the interface says "Ajustes" in one and "Configuración" in the other. **(owner: separate choices)**

How dates are written is a second setting, separate from the language, because the two do not
always go together. **(owner)**

## 2. Goals

- Every string in `ui/src` comes from a catalogue. None is written inline in a component.
- The strings are easy to find and manage: one JSON file per language in one folder, grouped by
  screen. A missing or misspelt key is a type error. A key missing from a language fails a test.
- The interface uses an established library, not one written for Exhibit. **(owner)**
- The library's information is stored per language. Switching back to a language used before is
  instant. A language used for the first time fills in during a background fetch, and nothing is
  matched again. **(owner: storage of data in different languages)**
- Errors arrive as codes with parameters, and the window words them in the current language.
  **(owner)**
- A first start picks a sensible language from Windows, so most owners never open the setting.

## 3. Non-goals

- The CLI. It stays in English. **(owner: "the UI only")** It does follow the library's language
  setting for the information it fetches, because that lives in the core.
- mpv. Its audio and subtitle preferences stay with the owner's own mpv configuration.
  **(owner)**
- Languages beyond `en-US`, `es-ES` and `es-MX` for now. Adding one more should only need a
  catalogue file and one entry in a list.
- Translating the installer, the Windows menus or the README.
- Right-to-left layout.
- The stage 4 agent's language. Ask stays as it is; when the agent arrives, it takes the same
  setting.

## 4. Anti-goals

These are failures even if the code works:

- **A flash of English** before Spanish appears at startup.
- **English interface text** on a Spanish screen. English in the library's own information, where
  TMDB has no translation for the region, is accepted (section 9). **(owner)**
- **A confident wrong match** because a title was searched or scored in one language when the file
  is named in another.
- **A screen that breaks in Spanish.** Spanish runs about 25% longer than English, so titles,
  buttons, hints and placards must hold their layout at three metres.
- **More settings than needed.** There are exactly two new settings, Language and Date format, on
  the one Settings screen.
- **Losing the library's English.** The English text is always kept, because it fills any gap
  in a translation.
- **Text written into the database in English by the core** ("Season 2", "Episode 3") and shown
  as is in Spanish.

## 5. Constraints

The rules in `CLAUDE.md` all apply. These ones matter most here:

- Bun only.
- WebView2 only in `ui/src`; happy-dom gaps are stubbed in `ui/test/setup.ts`.
- Plain `rusqlite` and hand-written SQL.
- Tokens only in `tokens.css`.
- The UI reaches data only through Tauri commands.
- UI SDK for every control, including the new language and date-format pickers.
- TMDB facts, from its docs (`developer.themoviedb.org/docs/languages` and `/docs/image-languages`):
  - `language` takes ISO 639-1 plus ISO 3166-1 (`es-ES`, `es-MX`), and the default is `en-US`.
  - A missing translation comes back as an empty string. The docs promise no fallback.
  - Person names and characters are mostly not translated.
  - `poster_path` comes in the requested language first, then from the work's original language,
    then as the highest-rated poster overall.
  - Backdrops and episode stills do not depend on the language.
  - Images are tagged by base language only (`es`). Regional variants are not supported for
    images.
  - Search matches original, translated and alternative titles. Results come back in the
    requested language.

## 6. Approaches

### Interface strings

1. **i18next with react-i18next (picked).**
   - It is the most widely used and tested option.
   - Its fallback chain fits the regional choice: `es-MX → es → en-US`. Shared Spanish lives once
     in `es.json`. `es-ES.json` and `es-MX.json` hold only the words that differ.
   - Keys can be typed from `en-US.json`.
   - Plurals come from `Intl.PluralRules`, and interpolation is built in.
   - It needs no build transform, so Vite and `bun test` run it unchanged.
2. **Lingui or Paraglide.** These are checked at compile time and smaller. Each needs a build
   transform that both Vite and `bun test` would have to run, and regional fallback is clumsier.
   Rejected.
3. **react-intl (FormatJS).** It uses solid ICU messages, but partial regional catalogues would have
   to be merged by hand. Rejected.

### Information per language

1. **A translation table beside `items` (picked).**
   - What does not change with language stays on `items`: the TMDB id, year, runtime, backdrop,
     match, people and play state.
   - The English text stays on `items` too, as the base.
   - A new table holds one row per item per other language used.
   - Reading takes the current language's text and falls back field by field to the base. This
     is plain SQL with `coalesce(nullif(...))`.
2. **A JSON blob per item, keyed by language.** It is quicker to write, but search, sort and genre
   filtering would have to dig into JSON. Rejected.
3. **Fetch again and overwrite.** One language is stored at a time, so every switch costs a full
   fetch. Rejected: the owner asked for storage in each language.

### Date format

The setting is separate from the language. **(owner)** Its choices are:

- **Automatic:** follows the language.
- **Day first:** 20 November 2026.
- **Month first:** November 20, 2026.
- **Numeric:** 2026-11-20.

With `en-US` and Automatic, dates read "November 20, 2026" instead of today's fixed `en-GB` "20
November 2026". Day first gives the old look back. (Designer's call)

Month names always follow the language. This is built from `Intl.DateTimeFormat#formatToParts` in
the current language, with the parts put in the chosen order. Numbers (file sizes, counts) follow
the language.

## 7. Settings

- **Language:** `en-US` (English), `es-ES` (Español: España), `es-MX` (Español: Latinoamérica).
  - Each choice is written in its own language, so someone who cannot read the current one can
    still find theirs.
  - It is stored in the core's `settings` table under `language`, because the core needs it for
    TMDB.
  - With nothing stored, the core takes a default from the Windows display language:
    - `es-ES` for Spanish (Spain);
    - `es-MX` for any other Spanish region;
    - `en-US` for everything else.
  - The default is used until the owner chooses, and is not written to the database.
- **Date format:** `auto`, `day`, `month` or `numeric`, stored under `date_format`. The default is
  `auto`.
- Both appear on the one Settings screen as single choices, built on UI SDK, and reachable with
  the d-pad. The look follows the existing Settings sections and is shown to the owner before it
  is final.
- `boot` returns both settings. The window starts i18next in the right language before its first
  frame, so there is no flash of English (the intro already covers boot).
- Changing the language:
  1. switches the interface in the same frame;
  2. sets `<html lang>`;
  3. starts the background fetch (section 9) when the library has no text in that language yet.

## 8. Interface strings

- **Where they live:** `ui/src/i18n/`:
  - `index.ts` sets up i18next and exports a typed `useT` (or uses react-i18next's
    `useTranslation` directly);
  - `locales/en-US.json` is the source of every key;
  - `locales/es.json` holds the shared Spanish;
  - `locales/es-ES.json` and `locales/es-MX.json` hold only the regional differences.
- **Keys** are grouped by screen or component, named for meaning rather than wording:
  - `settings.language.label`;
  - `details.play`, `details.resume`;
  - `errors.source_offline`.
- **Types:** i18next's `CustomTypeOptions` types the keys and their parameters from `en-US.json`.
  A wrong key is a type error.
- **Tests:**
  - every key in `en-US.json` resolves to a Spanish string through `es-ES → es` and through
    `es-MX → es`;
  - no catalogue has a key that `en-US.json` lacks;
  - every placeholder (`{{count}}`) in English appears in each translation.
- **Formatting** goes through one module (today's `format.ts` and the date in `tools.ts`). It reads
  the current language and date format instead of the fixed `en-GB` and `["en"]`. Language names
  for audio and subtitle tracks use `Intl.DisplayNames` in the current language.
- **Labels the core writes today:** the core stores "Season N" and "Episode N" as titles
  (`identify_show.rs`). The window words these from the season or episode number instead:
  - "Season 2" or "Temporada 2";
  - "Specials" or "Especiales" for season 0;
  - "Episode 3" or "Episodio 3".
  A TMDB episode title, when there is one, is still used.
- **On-screen keyboard:**
  - in Spanish, the letters page gains `ñ`;
  - the accented vowels (`á é í ó ú ü`) and `¿ ¡` go on the symbols page.
  - Search already ignores accents (FTS5 `unicode61` removes diacritics), so typing without
    accents still finds "Película".
  - The layout is shown to the owner before it is final.
- **Text that stays as it is:** proper names (Dolby Atmos, DTS:X, mpv, TMDB) and the button
  letters A, B, X, Y.

## 9. Information per language (core)

### Data

- `items` keeps its columns. For a TMDB-matched item, its `title`, `overview`, `genres` and
  `poster` are the `en-US` text: the base. For an item with no TMDB match, they are the local
  text (the nfo's or the cleaned file name), which serves every language.
- New table (one migration):

  ```sql
  CREATE TABLE item_texts (
      item_id  INTEGER NOT NULL REFERENCES items(id) ON DELETE CASCADE,
      lang     TEXT NOT NULL,          -- 'es-ES', 'es-MX'
      title    TEXT NOT NULL DEFAULT '',
      overview TEXT NOT NULL DEFAULT '',
      poster   TEXT,                   -- cached file name for this language, or NULL
      PRIMARY KEY (item_id, lang)
  );
  ```

  An empty field means "no translation" and falls back to the base, `en-US`, never to the other
  Spanish region. **(owner)** Only the language in effect is fetched and stored, so some English
  shows through where TMDB has no translation for that region, mostly in episode overviews.
  That is accepted. Movies, shows, seasons and
  episodes all get rows; season rows carry only the poster.
- **Genres** become TMDB genre ids on `items` (`genre_ids`, a JSON array). Their names come from
  a `genres(id, lang, name)` table filled from `/genre/movie/list` and `/genre/tv/list` in each
  language used. The genre filter matches by id, so it works in any language.
  - The migration has to turn today's English names back into ids; the builder settles how
    (a lookup against the `en-US` genre list, which is fixed and small).
- **Posters** are cached per language: `movie-603-poster.es.jpg` beside today's
  `movie-603-poster.jpg`, which stays as the `en-US` poster. Backdrops and stills are shared.
  - A language's poster is stored only when TMDB has a poster tagged with that language.
    TMDB's `poster_path` falls back to the original language's poster, so it cannot be used as
    is. Ask for the images with `include_image_language=es` and take the top-rated one.
    Otherwise `poster` stays NULL, and the English poster shows. (Designer's call: without this,
    a Japanese film in a Spanish library would switch to its Japanese poster and change its
    tint.)
  - Candidate posters in the match picker follow the same naming, so a search in Spanish never
    overwrites the English poster file.
- **Reading:** every query that returns text (`query.rs`, `rows.rs`) joins `item_texts` for the
  current language and takes `coalesce(nullif(t.title, ''), i.title)` and so on. The current
  language is read from the settings once per `Library` call, not passed in by the window.
- **Search:**
  - the full-text index covers the base text and every stored translation, so "Fight Club",
    "El Club de la Lucha" and "El club de la pelea" all find the film;
  - the triggers keep it in step with `item_texts`;
  - results show in the current language.

### Fetching

- `TmdbProvider` methods take the language (`movie(id, lang)`, `show`, `season`, `search_*`, the
  genre lists). It sends `language=<tag>` on every call. When asking for images it sends the base
  code (`es`).
- **Identify** (new items) always fetches `en-US` for the base. When the setting is not `en-US`,
  it also fetches the setting's language into `item_texts`, so a Spanish library's new arrivals
  show in Spanish at once. That is two requests per item instead of one.
- **Matching does not depend on the setting.** (Designer's call)
  - A title is searched in every supported language (`en-US`, `es-ES`, `es-MX`). That is three
    searches per new item, at identify only.
  - The hits are merged by TMDB id.
  - Each hit is scored against its title in each language and its original title.
  - The confidence thresholds do not change, and the 13-of-13 check on `D:\Movies` must still
    pass.
  - So the same file gets the same match in any language. "El viaje de Chihiro", "Spirited Away",
    "El Club de la Lucha" and "El club de la pelea" all match, in an English library as well as
    a Spanish one.
  - Candidates in the match picker show the current language's title.
- **Filling a new language:**
  - whenever the language in effect has no stored text, a worker job is queued. That includes a
    default taken from Windows that the owner never chose. It fetches the text for every
    matched movie, show, season and episode by TMDB id, and the genre lists;
  - nothing is matched again;
  - progress shows the way the other worker jobs show it;
  - each item shows its English text until its row arrives, and the screens update through the
    existing `data_version` polling;
  - without a TMDB key, or offline, the job waits and runs when TMDB can be reached. The window
    keeps showing English and says why, in the language chosen;
  - switching back to a language already stored needs no fetch.
- **Refresh** of one item (`Library::refresh`) refreshes its base and its current-language row.
- **Rate:** TMDB allows about 50 requests a second. The job paces itself below that and
  can be cancelled by switching the language again.

## 10. Errors as codes

- `ApiError` gains `code` and `params`:
  `{ kind, code: "tmdb.key_rejected", params: { … }, message }`.
  - `kind` stays.
  - `message` stays as the English detail for the CLI and logs.
- **Codes** are stable, dotted and named for what happened:
  - `source.offline` with `{ path }`;
  - `tool.not_found` with `{ tool, path }`;
  - `tmdb.key_rejected`;
  - `tmdb.unreachable`;
  - `tmdb.http` with `{ status }`.
- In the core, the error sites that can reach the window carry a code. That is a subset of the
  144 sites; the builder audits which. Internal errors (`db`, `io`, programming errors) share one
  code per kind.
- **The window** shows `t("errors." + code, params)`. When a code has no entry, it falls back to
  `t("errors.kind." + kind)`, a plain sentence per kind. It never shows the raw English message.
- This replaces `KEY_REJECTED` and its duplicated-string test. `plain()` in `api.ts` becomes this
  lookup.
- Each error message says what happened and what to do, in both languages, per `CLAUDE.md`.
- `JobStatus.last_error` carries the same code and parameters instead of a bare string.

## 11. Testing

Tests support the work; they are not the deliverable.

- **Rust:**
  - `item_texts` read fallback, field by field;
  - per-language poster names;
  - matching a file named in either language;
  - the fill job skipping items that already have the language;
  - the genre-id migration;
  - the codes on the errors that reach the window.
  - Uses the existing TMDB fixtures plus Spanish fixtures for one movie, one show and one season.
- **UI:**
  - catalogue completeness (section 8);
  - date-format output for each choice in each language;
  - a smoke render of each screen in `es-ES`.
- **In the running window:**
  - walk every screen in `es-ES` and `es-MX` with keys and screenshots, checking layout and
    length at 1920×1080;
  - switch the language on the dev library and watch the fill job;
  - switch back and confirm it is instant.
